Data Cleaning: A Necessity or a Failure of System Design?

Investigating preventable data quality issues in databases, spreadsheets and controlled data collection systems.

25 November 2026 · Technical article · Real-world data audit

1. Introduction

Why is cleaning data considered an unavoidable part of data analytics when software systems have long offered tools to prevent invalid information from being recorded?

Companies operated complex industrial, commercial and financial systems in the 1990s, before modern AI became widespread. They already used relational databases, spreadsheets and statistical methods to manage information. Data quality was already an established research topic [1]. Today, analysts routinely learn to remove duplicates, handle missing values and correct inconsistent formats. But some of these operations address problems that could have been prevented at the point of collection.

Consider a salary field. If a company's approved range for a particular job category is known, a database or spreadsheet can flag a value of €30,000 when that amount falls outside the range. Waiting for an analyst to discover the error in a monthly report introduces avoidable rework. However, a plausible but incorrect salary may still pass every validation rule.

This article examines that distinction using real commercial transaction data. Its purpose is not to question the usefulness of data analysts but to investigate the boundary between preventive system design and necessary analytical preparation.

2. Scope and terminology

The study focuses on information sources an organisation can design or control: relational databases, Excel, Google Sheets, electronic forms, web applications, APIs and structured file imports. It examines predictable violations of explicit rules, rather than sensor noise, unavailable information or unverified external data.

ConceptMeaningExample
ValidationChecking compliance with a specified ruleA required invoice number is present
CleaningInvestigating or correcting problematic recorded valuesResolving a missing invoice reference
TransformationChanging representation for a particular useAggregating line items into invoice totals
AccuracyAgreement with the real-world eventThe recorded price is the actual price charged

Data may be valid without being accurate, and preparation for analysis is not necessarily cleaning. The research question is how far controllable, rule-detectable errors can be prevented during design without excluding legitimate transactions.

3. Quality by design

Validation can be applied before acceptance, at storage and during integration. The important distinction is when a violation is detected and whether the source can be corrected.

SourceDesign controlWhat it can prevent
Relational databasePRIMARY KEY, FOREIGN KEY, NOT NULL, CHECKSpecified integrity violations
Excel / SheetsValidation lists, range rules, protected cellsMany invalid direct entries
Web form / APIRequired fields, schema and server-side validationInvalid submissions
CSV importSchema, type and reference checksNon-conforming imported rows

Controls should be enforced at the appropriate trust boundary, not only in the user interface. Spreadsheet copy/paste and imports can bypass ordinary direct-entry validation. An API should validate server-side, even when its form already checks input [2,3].

5. Data quality findings

5.1 Missing values

Six core transaction fields are complete. This is consistent with upstream validation or later processing, but the exported workbook does not establish which mechanism was responsible. CustomerID should not automatically be declared mandatory: the business may support transactions without an identified customer. Description could be obtained from a product reference table, provided that product and adjustment codes are properly modelled.

5.2 Repeated observations

There are 5,268 exact repeated rows beyond their first occurrence (0.97%). An exact match is not sufficient proof that a transaction was recorded twice. Two genuinely distinct lines can have identical observable attributes. The workbook contains no separate line identifier.

A unique transaction-line key and idempotent submission logic could prevent retry-induced duplicates. Without source identifiers or logs, the observed 5,268 repeats remain candidates for investigation, not confirmed errors.

5.3 Quantity and price

All 9,288 cancellation lines have negative quantities. They account for 87.42% of the negative-quantity observations. The remaining 1,336 negative quantities need business context. Zero quantity never occurs. The 2,515 zero-price lines require investigation rather than automatic deletion.

7. Implementation examples

7.1 Relational databases

A proposed transaction model includes a stable line identifier, a declared transaction type, and a quantity rule appropriate to that type. Price validation should reflect approved policies for discounts, free items and accounting adjustments.

CREATE TABLE transaction_lines (
    line_id TEXT PRIMARY KEY,
    invoice_no TEXT NOT NULL,
    event_type TEXT NOT NULL
        CHECK (event_type IN ('SALE','CANCEL','ADJUSTMENT')),
    quantity INTEGER NOT NULL,
    unit_price DECIMAL(12,2) NOT NULL,
    CHECK (
        (event_type = 'SALE' AND quantity > 0)
        OR (event_type = 'CANCEL' AND quantity < 0)
        OR event_type = 'ADJUSTMENT'
    )
);

The example illustrates the principle; production designs also need authorised adjustment workflows, references, exception handling and migration rules. The new line identifier and event type are proposed source-system attributes, not existing workbook columns.

7.2 Excel and other spreadsheets

A controlled workbook can separate raw entry from reports, require transaction type through a dropdown, and use custom validation to check the quantity. For example, with event type in B2 and quantity in C2, a proposed Excel formula is:

=OR(AND(B2="SALE",ISNUMBER(C2),C2>0),
    AND(B2="CANCEL",ISNUMBER(C2),C2<0),
    AND(B2="ADJUSTMENT",ISNUMBER(C2)))

Use a Stop alert, configure blank handling deliberately, and validate bulk imports separately. Excel is not a relational database and cannot enforce every cross-record rule reliably.

7.3 Applications and APIs

Validate incoming fields on the server, return a clear error message, and retain the rejected event in an appropriate review queue when needed. A corrected submission should be traceable, and retries should use stable identifiers. The database provides a final integrity boundary even if multiple applications write to it.

8. Discussion and limitations

The case study shows why cleaning should begin with understanding the business process rather than applying generic removal functions. The 9,288 cancellation lines demonstrate how a superficially reasonable positive-quantity constraint can reject valid event types. Exact repeated rows demonstrate why entity identity needs to be designed, not guessed after export.

The audit cannot prove that the original retailer lacked preventive controls or that particular observations are incorrect. We do not have its source schema, business policies, entry logs or verified ground truth. We have not measured manual cleaning time, financial savings, native Excel behaviour or actual deployment of proposed rules. These require a controlled follow-up experiment with documented business requirements.

Prevention has an implementation and maintenance cost. It is most valuable when a rule is stable, predictable, repeatedly violated and inexpensive to enforce. A rule that rejects legitimate transactions can create a new data quality problem. Rejection is therefore not equivalent to correction.

9. Conclusion

Data cleaning is necessary when information needs investigation or correction, but it should not be accepted as the inevitable response to every predictable data quality problem. When an organisation controls its information systems, explicit rules can often be implemented at the point of entry, storage or import.

The Online Retail audit supports a design principle rather than a numerical claim about the proportion of avoidable errors: understand the business event, define its semantics, enforce appropriate constraints and preserve legitimate exceptions. Where recurring violations can be traced to a controllable source, the objective should be to resolve the cause rather than repeatedly repair its consequences.

For data analysts, this means contributing not only to reliable reports but also to the feedback that improves upstream systems. A mature data workflow makes quality verification routine while reducing avoidable correction.
